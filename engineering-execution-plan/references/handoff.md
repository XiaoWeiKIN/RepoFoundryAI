# 从工程事实生成面向负责人的说明

用于解释既有 ADR、EP 的进展、取舍或验收依据。先回答读者当前的问题，再按需展开。
直接在对话中交付；只有用户要求保留，或确有独立阅读用途时，才保存派生视图。
本指南不增加 schema 字段、必填章节、审批步骤或独立生命周期。

## 按阅读目的选择内容

| 读者当前目的 | 首先回答 | 事实入口 |
|---|---|---|
| 掌握进展 | 哪些行为已改变、还差什么、下一步是什么 | Purpose、Current Snapshot、Blockers、status |
| 决定方案 | 推荐什么、代价是什么、什么情况会推翻推荐 | ADR、Design、Decision Log、Research 输入 |
| 检查交付 | 哪项行为由什么证据支持、哪些边界尚未验证 | Compliance Matrix、Validation、实际验证 revision 与 artifacts |

选择当前需要的一种说明；不要每次都输出三份报告。根 EXECPLAN.md 继续保持自包含，
阅读视图只提供理解入口，不能让接手 Agent 依赖另一份摘要才能继续。

## 交接优先说明变化和影响

存在可核对基线时，先说明相对哪个 checkpoint、revision 或上次评审发生了变化。
聚焦行为、范围、假设、证据和阻塞的增量，并解释它们为何影响交付或决定。
没有可靠基线时，只报告当前事实；不要把未读取的历史描述为“没有变化”。

从现有 section、代码差异和验证记录获取事实。status 的计数和 completion 信号
由 CLI 提供；ready_to_archive 只表示结构上的候选状态，不证明实际验收已经执行。
区分尚未运行、已运行失败、证据已过期和已通过，不把“计划验证”写成“已经验证”。

若确有待决定事项，给出推荐、替代方案、代价和对应的具体制品版本。已有授权时继续
推进；没有实质决定时直接说明下一动作，不制造确认点。ADR 和 Design 的授权仍按
各自契约处理，阅读视图不能扩大或替代授权。

## 用清晰语言保留工程精度

先说可观察行为，再解释内部术语。使用明确主语、短句和一致名称；保留条件、例外、
否定约束和精确标识符。用自然语言区分事实、推断、建议和待验证事项，不要求逐句打标签。

例如，某次维护功能的说明可以先写：

> 系统会在日常检查时提示哪些 ADR 需要维护，并提供下一步预览命令。检测不会修改
> ADR，普通维护告警也不会导致校验失败。

随后按需展开策略、阈值和退出码。这是表达示例，不能作为任何仓库的已实现结果。
约束的通俗解释就近链接 ADR-NNN#C-NNN；消费者所需的原文、capsule 和 evidence pin
继续使用既有工具，不用改写后的说明替代。

## 图和交互只解决具体理解问题

- 依赖或替代关系难追踪时，用关系图，并保留节点 ID 与来源。
- 发布、故障和回滚难理解时，用状态图或时序图，标出失败与恢复路径。
- 参数或方案需要探索时，按需生成交互页面，区分假设模拟与实测结果。

文字足以解释时无需附图。附加视图不形成新的 gate，也不触发 Case Study、发布或
视频制作。可复用的演示结论仍需回到对应证据，图中的箭头不能凭空制造依赖或因果。

## 保持来源和版本可追溯

关键判断就近链接到具体 section、约束、实现或验证记录。说明制品 revision 与实际
验证 revision；相关实现尚未提交时说明工作树差异，不能只用 HEAD 冒充完整快照。
保存的派生视图注明生成时间与来源版本；来源变化后重新读取并核对，再将它作为
当前说明交付。没有自动刷新机制时，不声称已自动检测或修复过期内容。

发现摘要与源冲突时，呈现冲突并回到源核对。不得为了让视图一致而改写 accepted ADR、
sealed Checkpoint、approved snapshot 或 archived EP。历史视图保留当时版本边界。

交付前用读者的问题自检：能否找到关键变化、识别未验证边界，并定位支持结论的证据？
这是一项语义检查，不以字数、图表数量、阅读时间承诺或综合分数作为新的机械门禁。
