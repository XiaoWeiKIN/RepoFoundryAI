# 把科学方法用于工程基准测量

方法来源：用户提供的 `golang-benchmark/METHODOLOGY.md`（《方法论：把科学方法用在
基准测试上》）。这里保留“先假说、后实验、可证伪、可重复、证据公开”的约束，
并扩展到服务容量、存储、分布式系统和持续回归；使用本 Skill 不需要访问来源仓库。

## 从问题推导预测

先写问题、假说和证伪条件，再运行用于检验它的基准。已有数据可以帮助提出假说，
但必须标为探索证据；不能把同一批数据包装成事前预测的验证。实测校准也属于探索，
须保留结果，并在后续独立 Run 中检验修订后的假说。

机制问题要能区分解释。例如“缓存命中减少了后端读取，所以延迟下降”，不能只测延迟；
还应预测相同请求集下的后端读取次数，并说明哪些结果会推翻该机制。

Scenario 的 `Question and Hypothesis` 可直接使用下面的结构：

| 假说 | 预测与证伪条件 | 检验方式 |
|---|---|---|
| H1：在指定数据集和并发下，命中缓存使后端读取次数下降 | P1：预热后的重复读取无后端请求；仍有后端请求则推翻此预测 | 后端计数、请求 Trace、缓存分支源码 |
| H2：指定资源配置能承载目标到达率且满足 SLO | P2：在预声明窗口内，完成率、错误率、延迟均满足既定阈值；任一可靠越界则否定声明 | 到达/完成计数、延迟分布、队列与资源诊断 |

H2 是可直接验收的行为声明，不必假装已经解释容量瓶颈。若继续声称“瓶颈在锁竞争”，
就需要提出并检验新的机制预测。`passed` 始终只表示满足 Scenario 的判定规则，
不表示所有解释已被证明。

## 让差值可以归因

先确认输出语义、实际工作量和输入分布等价，再控制实现以外的条件。把已知混杂因素
写进 `Variables`，例如版本升级同时改变算法和默认配置，就不能将差值全归因于算法。
多因素研究用预声明的实验矩阵分离主效应和交互效应；没有这样的设计，只解释组合效果。

输入既要有能隔离机制的最小用例，也要覆盖声明所针对的实际分布。小输入、热缓存、
重复值或静态表命中可以研究，但必须命名为专门场景，不能代表未测量的线上负载。

有效性检查随被测系统选择：

- 编译型代码：检查目标调用和必要计算是否仍在计时路径；保活或 sink 本身是否改变了
  逃逸、分配或其他待测机制。诊断构建的优化选项必须与被测构建对应，差异需说明。
- 服务压测：核对发起数、完成数、错误数和实际完成的业务工作；确认压力发生器没有
  先饱和，明确开放/闭合负载模型以及排队和超时是否进入延迟统计。
- 存储或缓存：核对实际 I/O、命中率、数据量和冷热状态，而不只相信客户端耗时。

检查失败时先记录无效实验并修复测量，再创建新 Run；不能把空跑的数字纳入性能结论。

## 重复测量与不确定性

Scenario 写清什么算一个样本：请求、迭代、进程运行或独立部署。单个进程内的百万次
请求不能自动当作百万次独立环境重复。区分请求延迟分布的 p99 与估计量的置信区间。

在同一受控环境中交错或随机化对照/候选的测量顺序，记录背景负载和预热条件，减少
时间漂移带来的混杂。对照与候选使用同一协议；跨机器数字需先说明环境差异。

微基准默认至少 8 次重复。长时间容量或故障实验按成本、波动和判定精度预声明独立
重复策略及其理由，不机械套用微基准次数。单次试跑只能作为观察，不能据此建立稳定基线。
报告样本数、适合该指标的汇总、效应大小、区间或离散程度及其定义，不只给一个百分比。

分析前固定排除规则与停止条件。保留被排除的样本及原因，不能因“太慢”删样本；
若采用序贯方法，事先声明对应判定方法。噪声掩盖了目标差值、样本不足或区间无法支持
预声明判断时，报告 `inconclusive`，不把“未发现差异”写成“等价”。

## 三条证据链和结论强度

每个机制结论逐项对应：

1. 测量：指标变化、单位、重复样本、不确定性及原始输出。
2. 诊断：编译器输出、汇编、profile、Trace、运行时计数或实际 I/O，证明所述路径发生。
3. 源码：被测版本的具体分支、常量或数据结构，解释诊断与数字为何一致。

编译器证据不适用时使用相应运行时诊断，不为非 Go 系统强加逃逸分析。
源码不可获得时明确缺口，只给诊断支持的解释或行为结论。数字满足门禁但机制证据冲突时，
可以按原规则报告门禁结果，同时明确机制尚未确认；若该证据本就是必需条件，则依规则
判为 `inconclusive` 或 `failed`，不得临时降级规则。

Result 的 `Interpretation` 逐条列出预测、观察、证据位置和“支持 / 推翻 / 证据不足”。
被推翻后保留原假说，在 `Contradictions and Supersession` 写触发观察、无效设计、
修正与后续 Scenario/Run；没有翻车就如实写无，不编造过程。

## Go 微基准的应用

- 机制预测优先使用 `allocs/op`、`B/op`、逃逸/内联诊断和栈帧/汇编等可核对证据；
  `ns/op` 用于衡量时间影响，不能独自证明逃逸或分配机制。分配指标也绑定输入、
  Go 版本、架构和编译选项，不宣称无条件跨机器不变。
- 正式测量默认 `go test -run '^$' -bench '<pattern>' -benchmem -count=8 <package>`，
  使用 benchstat 汇总与比较，保留工具版本、原始输出、样本数及区间/波动说明。
  置信区间与最小样本要求按所用 benchstat 版本确认，不把固定次数当成统计充分性保证。
- 查看仓库的 Makefile 或 harness 后再使用 `make bench`、`make escape`、`make frames`
  等目标；这些名称是来源仓库约定，不假定其他项目存在。
- 对零分配、异常低耗时或违背预测的结果，查看实际优化构建的逃逸/内联诊断与反汇编，
  确认目标操作仍被执行。可用编译器 `-m`、`-S` 或 `go tool objdump`，保留精确命令。
  禁止只用关闭内联的诊断去解释开启内联的基准。
- 使用 `b.Loop()` 或其他循环/保活写法前，按被测 Go 版本的官方文档和生成代码核实
  优化与计时语义；不能仅凭 API 名称断言被测工作不会被消除。

## 与现有制品对应

Scenario 承载问题、假说、预测、设计和事前判定规则；Result 承载数据、预测核对、
三条证据链、边界和翻车记录。无需再创建一份重复的专题 README。

原始数据放在 Run 的 `artifacts/`。若 harness 使用 `.bench/`，封存前把对应原始输出
纳入证据目录并记录生成命令，不能只留下 benchstat 摘要。记录硬件、OS、架构、
工具链与依赖版本、构建参数、重复次数和执行身份，让每个数字可追溯、命令可复现。

结论明确区分规范保证与实现细节，绑定已测版本、架构、负载和规模；指出失效条件，
不将最小用例外推为所有环境成立的规律。
