# 发布前复核

按顺序完成。任何一项不成立时保持 `status: draft`。

## 1. 中心主张

- 第一屏能用一句话说明文章判断和读者收益。
- 每节都支撑中心主张；无关但有趣的材料已删除。
- 标题表达判断，不是“背景、实现、总结”的空目录。

## 2. 来源与事实

- 所有关键机制都回到指定 revision 的代码或 schema。
- 设计动机来自 ADR、Research、EP Decision Log 或明确作者说明。
- 结果来自测试、CI、benchmark、运行观察或用户提供的证据。
- active、review-ready、proposed、completed 等生命周期没有被混写。
- 推论已标明，未测量的效率、成本和性能数字已删除。
- `source_revision` 可恢复；dirty 工作区边界已说明。

## 3. 叙事质量

- 输出语言符合用户选择；英文是独立成文而非逐句直译。
- 文章讲清“压力 → 判断 → 机制 → 证据 → 边界”，没有按文件或日期流水记账。
- 只保留真正改变路线的过程事件。
- 专有术语首次出现时已解释。
- 代码、表格和 Mermaid 都帮助理解关键关系，没有装饰性内容。
- 已删除 AI 套话、重复结论和无主语的模糊判断。

双语模式还必须确认：

- 两份文章的中心主张、数字、revision、生命周期和证据一致。
- 项目术语翻译一致，代码标识符保持原始拼写。
- 两份文章互相填写 `translation_of`，且都能独立阅读。

## 4. 当前适用性

- 开头声明 Case Study 不替代当前规范。
- 已链接项目当前规范、产品契约或模块入口。
- 历史路径、命令和 API 明确标注日期或 revision。
- 已说明哪些结论仍适用、哪些已经被替代。

## 5. 安全与公开边界

- 无 token、cookie、密码、内部凭据或个人信息。
- 内部域名、租户名、客户数据、组织结构和容量数字已确认可以分享或已脱敏。
- 截图、日志和请求示例没有隐含敏感字段。
- 第三方文本和图片没有超出许可或合理引用范围。
- 对外宣传性结论没有超出工程证据。

## 6. 仓库完整性

- Markdown 本地链接可解析且使用仓库相对路径。
- 代码路径、EP、Research、ADR 和 evidence 路径存在。
- 新案例已加入仓库 Case Studies 索引。
- 没有覆盖用户已有同名文件或无关工作树改动。
- 适用的文档检查、lint 或测试已经运行并记录结果。

## 状态

默认使用：

```yaml
status: draft
language: zh-CN
last_verified:
```

用户明确要求定稿或可发布，且以上检查全部通过后，使用：

```yaml
status: verified
last_verified: YYYY-MM-DD
```

`verified` 只表示文章在 `source_revision` 上完成来源与发布复核，不表示内容会自动
追随未来代码。代码或规范发生实质变化后，重新验证、明确标记为历史案例，或保留
旧 revision 边界。
